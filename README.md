# Synapse API

REST API на Go с PostgreSQL для регистрации и управления пользователями. 

Аутентификация основана на JWT в cookie (`access_token` и `refresh_token`), авторизация — на актуальной роли пользователя в БД (`user` / `admin`). 

Контракт API: [`docs/openapi.yaml`](docs/openapi.yaml). 

В работающем сервисе документация доступна по `/docs`, спецификация — по `/openapi.yaml`.

## Требования и запуск

- Docker и Docker Compose; либо Go 1.23+ и PostgreSQL 16.
- Скопируйте шаблон окружения: `cp .env.example .env`.

### Docker Compose

```bash
docker compose up --build
```

- API: `http://localhost:8080`
- Swagger UI: `http://localhost:8080/docs`
- OpenAPI YAML: `http://localhost:8080/openapi.yaml`
- Health check: `http://localhost:8080/health`

Порт хоста задаётся `API_HOST_PORT` (по умолчанию `8080`).

Внутри Compose API подключается к базе по hostname `postgres`.

Не меняйте его на `localhost` внутри контейнера API.

### Локальный запуск API без Docker

1. Запустите PostgreSQL.
2. Укажите локальные параметры БД в `.env`. Для запуска API на хосте используйте `POSTGRES_HOST=localhost` и `POSTGRES_PORT=5432` либо соответствующий `DATABASE_URL`.
3. Запустите API:

```bash
go run ./cmd/api
```

### Пересоздание БД в локальной разработке

Таблицы создаются из `internal/db/init.sql` при первом создании каталога данных PostgreSQL. 

Если volume `pgdata` уже существует, init-скрипт повторно не запускается. `docker compose down -v` удаляет volume и **все данные БД**. 

Используйте эту команду только если потеря данных допустима.

| ---------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |

| `API_HOST_PORT`        | Порт хоста для Docker                                                    | `8080`                                                                                     |
| `APP_ENV`              | Имя/окружение приложения                                                 | `synapse-backend`                                                                          |
| `DATABASE_URL`         | Полная строка подключения к PostgreSQL; имеет приоритет над `POSTGRES_*` | Если не задана, URL строится из `POSTGRES_*`                                               |

| `POSTGRES_PORT`        | Порт БД                                                                  | `5432`                                                                                     |

| `ACCESS_TOKEN_TTL`     | Срок access-токена                                                       | `15m`                                                                                      |
| `REFRESH_TOKEN_TTL`    | Срок refresh-токена                                                      | `168h` (7 дней)                                                                            |
| `ADMIN_REGISTER_TOKEN` | Секрет для `POST /api/v1/register-admin`                                 | Обязательно; замените перед запуском                                                       |
| `COOKIE_SECURE`        | Флаг `Secure` cookie                                                     | В конфигурации приложения по умолчанию `true`; для локального HTTP можно поставить `false` |
| `COOKIE_SAMESITE`      | Политика SameSite                                                        | `Lax`; поддерживаются `Lax`, `Strict`, `None`                                              |
| `COOKIE_DOMAIN`        | Domain cookie                                                            | Пустое значение по умолчанию                                                               |
| `CORS_ORIGINS`         | Разрешённые frontend origins, через запятую                              | В шаблоне указаны localhost origins; настройте под фактический frontend                    |
| `LOGIN_RATE_LIMIT`     | Число запросов login за окно                                             | `10` за 15 минут                                                                           |
| `REGISTER_RATE_LIMIT`  | Число регистрационных запросов с IP                                      | `10` за час для `/register` и `/register-admin`                                            |
| `REFRESH_RATE_LIMIT`   | Число refresh-запросов                                                   | `30` за минуту                                                                             |

При `COOKIE_SECURE=true` браузер отправляет cookie только по HTTPS. 

Для production используйте HTTPS и уникальные секреты. Не коммитьте настоящий `.env`.

## HTTP и формат ошибок

API находится под префиксом `/api/v1`. Запросы с JSON должны передавать `Content-Type: application/json`.

- Максимальный размер тела для методов с body — **1 MiB**. Превышение возвращает `413 PAYLOAD_TOO_LARGE`.
- Некорректный JSON, неизвестные поля или несколько JSON-значений в одном теле возвращают `400 VALIDATION_FAILED`.
- JSON-декодер отклоняет поля, не описанные в структуре конкретного запроса.
- Ответы API под `/api/v1` помечаются `Cache-Control: no-store, no-cache, must-revalidate, private` и `Pragma: no-cache`.
- Общая форма ошибки (`details` может отсутствовать):

```json
{
  "error": "VALIDATION_FAILED",
  "message": "Описание ошибки",
  "details": {
    "field": ["Причина ошибки"]
  }
}
```

Основные коды: 

- `400` — неверный запрос/валидация; 
- `401` — нет действительной аутентификации; 
- `403` — запрещённый origin/CSRF или недостаточная роль; 
- `404` — ресурс не найден; 
- `409` — конфликт уникальности; 
- `413` — тело слишком большое; 
- `429` — rate limit превышен; 
- `500` — внутренняя ошибка; 
- `503` — БД недоступна для проверки авторизации или rate limiting. 

Точный набор зависит от endpoint-а и стадии обработки.

## Аутентификация и CSRF

### Cookie-аутентификация

- `access_token` — короткоживущий JWT для защищённых маршрутов.
- `refresh_token` — JWT для обновления сессии; сервер хранит в PostgreSQL хеш refresh-токена, а не его исходное значение.
- Cookie устанавливаются с `Path=/api/v1/`, `HttpOnly`, `SameSite` и флагом `Secure` в соответствии с конфигурацией. Клиент не должен пытаться читать auth-cookie из JavaScript.
- Защищённый запрос должен отправлять cookie, например `fetch(url, { credentials: "include" })`.
- Middleware проверяет подпись, ожидаемый тип токена и срок действия, затем загружает пользователя по `sub` из БД. Пользователь должен существовать и иметь статус `active`; текущая роль также берётся из БД. Изменение роли или деактивация начинает действовать на последующих запросах. При ошибке БД доступ не разрешается.
- Роли: `user` и `admin`. Недостаточная роль даёт `403`; недействительный токен, удалённый пользователь или неактивный пользователь — `401`.

### Обязательный CSRF flow для браузера и cookie-клиентов

Все запросы, меняющие состояние (`POST`, `PUT`, `PATCH`, `DELETE`), требуют допустимый origin и CSRF-токен — включая публичные `/register`, `/register-admin`, `/login`, `/refresh` и `/logout`.

1. Выполните `GET /api/v1/csrf` с `credentials: "include"` и разрешённым заголовком `Origin` (браузер обычно устанавливает его автоматически). Если `Origin` отсутствует, endpoint проверяет origin из `Referer`. Если оба заголовка отсутствуют либо источник не входит в `CORS_ORIGINS`, возвращается `403 Недопустимый Origin`. Явно запрещённый `Origin` нельзя обойти разрешённым `Referer`.
2. Ответ содержит `csrf_token`; сервер одновременно устанавливает cookie `csrf_token` на `/api/v1/` с TTL 1 час. Эта cookie намеренно не `HttpOnly`, чтобы frontend мог прочитать значение.
3. Для каждого изменяющего запросa отправляйте `credentials: "include"`, заголовок `Origin` (браузер устанавливает его автоматически) и `X-CSRF-Token` со значением `csrf_token`. Значение заголовка должно совпадать с cookie.
4. При истечении CSRF-cookie получите новый токен через `GET /api/v1/csrf`.

Пример:

```js
const csrfResponse = await fetch("http://localhost:8080/api/v1/csrf", {
  credentials: "include"
});
const { csrf_token } = await csrfResponse.json();

await fetch("http://localhost:8080/api/v1/login", {
  method: "POST",
  credentials: "include",
  headers: {
    "Content-Type": "application/json",
    "X-CSRF-Token": csrf_token
  },
  body: JSON.stringify({ email: "user@example.com", password: "your-password" })
});
```

Сервер проверяет `Origin` по allow-list `CORS_ORIGINS`. 

Для `GET /api/v1/csrf` заголовок `Origin` обязателен: отсутствующий или неразрешённый источник отклоняется с `403`. 

Для изменяющих состояние запросов, если `Origin` отсутствует, middleware использует origin из `Referer`. 

Если он отсутствует или не разрешён, запрос отклоняется с `403`. CSRF-токен содержит случайный nonce и HMAC-подпись на `JWT_SECRET`.

Сравнение выполняется сервером. CORS и `SameSite` не заменяют CSRF-проверку.

Небраузерные клиенты, которые используют cookie-аутентификацию, также должны получать и отправлять CSRF-cookie, `X-CSRF-Token` и допустимый `Origin`/`Referer`. 

Для них отдельного обхода CSRF middleware нет.

## API endpoints

Полные схемы запросов/ответов приведены в `docs/openapi.yaml`. 

Ниже - краткая справка по фактическим маршрутам. Если endpoint меняет состояние, к нему применяются общие требования CSRF.

### Служебные маршруты

| Метод и путь        | Назначение                                                  | Успешный ответ                                                                   |
| ------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `GET /health`       | Проверка доступности HTTP-приложения                        | `200`, `{"status":"OK"}`                                                         |
| `GET /docs`         | Swagger UI                                                  | HTML                                                                             |
| `GET /openapi.yaml` | OpenAPI YAML                                                | YAML                                                                             |
| `GET /api/v1/csrf`  | Выпуск CSRF-токена и cookie; требуется разрешённый `Origin` | `200`, `{"csrf_token":"..."}`; `403` без `Origin` или при недопустимом источнике |

### Регистрация и сессия

| Метод и путь                  | Доступ                                                   | Тело / заголовки                                      | Успех и важные ошибки                                                                                                                                                        |
| ----------------------------- | -------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v1/register`       | Публичный, CSRF обязателен                               | `email`, `password`, `first_name`, `last_name`        | `201`; `400` валидация; `409` email занят; создаёт `user` со статусом `active`                                                                                               |
| `POST /api/v1/register-admin` | Публичный, CSRF обязателен                               | Те же поля; секрет только в заголовке `X-Admin-Token` | `201`; `403` неверный секрет; создаёт `admin`                                                                                                                                |
| `POST /api/v1/login`          | Публичный, CSRF обязателен                               | `email`, `password`                                   | `200`, устанавливает `access_token` и `refresh_token`; `401` при неверных учётных данных или запрещённом входе                                                               |
| `POST /api/v1/refresh`        | Нужна cookie `refresh_token` и CSRF                      | Тело не требуется                                     | `200`, атомарно ротирует токены и устанавливает новые cookie; `401` при невалидном/повторно использованном токене; `500` при ошибке ротации; `503` при проблеме rate limiter |
| `POST /api/v1/logout`         | CSRF обязателен; refresh-cookie фактически необязательна | Обычно без тела                                       | `200`, очищает auth-cookie; если refresh-cookie присутствует, отзывает токен; `500` при ошибке отзыва                                                                        |

Пример тела регистрации/входа:

```json
{
  "email": "user@example.com",
  "password": "a-long-password",
  "first_name": "Ada",
  "last_name": "Lovelace"
}
```

Email нормализуется (обрезка пробелов и lowercase). 

Пароль для регистрации должен содержать минимум 8 символов и максимум 72 байта (ограничение bcrypt). 

Email и имена ограничены 255 символами. 

Ответ login не возвращает JWT в JSON - токены передаются через `Set-Cookie`.

### Текущий пользователь

Для следующих маршрутов нужна действительная `access_token` cookie и активный пользователь:

| Метод и путь             | Роль            | Поведение                                                                          |
| ------------------------ | --------------- | ---------------------------------------------------------------------------------- |
| `GET /api/v1/users/me`   | `user`, `admin` | Получить профиль текущего пользователя                                             |
| `PUT /api/v1/users/me`   | `user`, `admin` | Полная замена профиля: `email`, `first_name`, `last_name` обязательны              |
| `PATCH /api/v1/users/me` | `user`, `admin` | Частичное изменение одного или нескольких полей `email`, `first_name`, `last_name` |

Пользователь не может изменить собственную роль или статус через профильные маршруты.

### Администрирование пользователей

Все следующие маршруты требуют актуальную роль `admin` в БД:

| Метод и путь                | Поведение                                                                                                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/users`         | Список с пагинацией, поиском и фильтрами                                                                                                                                                    |
| `POST /api/v1/users`        | Создание пользователя; обязательны `email`, `password`, `first_name`, `last_name`; `role` необязателен (`user` по умолчанию, допустимы `user`/`admin`); статус нового пользователя `active` |
| `GET /api/v1/users/{id}`    | Получение пользователя по UUID                                                                                                                                                              |
| `PUT /api/v1/users/{id}`    | Полная замена редактируемых данных; обязательны `email`, `password`, `first_name`, `last_name`, `status`; текущая роль сохраняется, поле `role` не меняет её                                |
| `PATCH /api/v1/users/{id}`  | Частичное обновление; разрешены `email`, `password`, `first_name`, `last_name`, `status`; текущая роль сохраняется, поле `role` не меняет её                                                |
| `DELETE /api/v1/users/{id}` | Удаление пользователя; нельзя удалить себя или другую учётную запись с ролью `admin` (`403`)                                                                                                |

Для `PUT /api/v1/users/{id}` обязательны `email`, `password`, `first_name`, `last_name`, `status` (статус должен быть `active` или `inactive`).

Поле `role`, если передано, не используется.

Для `PATCH` допустимы поля `email`, `password`, `first_name`, `last_name`, `status`.

Все они необязательны, но нужно передать хотя бы одно поле. Статус принимает только `active` или `inactive`. 

Роль можно задать при создании пользователя, но существующая роль через эти PUT/PATCH маршруты не меняется.

### Поиск и пагинация

`GET /api/v1/users?page=1&limit=10&search=ada&role=user&status=active`

- `page`: целое число от `1`, по умолчанию `1`.
- `limit`: целое число от `1` до `100`, по умолчанию `10`.
- `search`: поиск по email, имени и фамилии; максимум 200 символов.
- `role`: необязательный фильтр `user` или `admin`.
- `status`: необязательный фильтр `active` или `inactive`.
- Ответ списка содержит `items`, `page`, `limit`, `total`, `total_pages`.
- Неверные параметры дают `400`.

## Rate limiting

Счётчики хранятся в PostgreSQL в таблице `api_rate_limits`, поэтому разделяются между экземплярами приложения. 

Используются fixed windows. 

Ошибка доступа к БД лимитера обрабатывается fail-closed и возвращает `503`.

| Маршрут                       | Ключ счётчика                                  | Начальное окно/порог   |
| ----------------------------- | ---------------------------------------------- | ---------------------- |
| `POST /api/v1/login`          | IP + нормализованный email из JSON             | 10 запросов / 15 минут |
| `POST /api/v1/register`       | IP клиента                                     | 10 запросов / час      |
| `POST /api/v1/register-admin` | IP клиента                                     | 10 запросов / час      |
| `POST /api/v1/refresh`        | Хеш refresh-cookie; при отсутствии cookie — IP | 30 запросов / минуту   |

При превышении возвращается `429 RATE_LIMITED` и `Retry-After`. 

Текущий login-limiter считает **все запросы**, а не только неуспешные попытки, поэтому он не полностью соответствует политике «10 неуспешных попыток за 15 минут». 

Он также не блокирует аккаунт только по имени пользователя. 

Порог настраивается переменными `LOGIN_RATE_LIMIT`, `REGISTER_RATE_LIMIT`, `REFRESH_RATE_LIMIT`. 

Длительности окон в текущей реализации заданы в коде.

IP берётся из TCP `RemoteAddr`. `X-Forwarded-For` и аналогичные заголовки не считаются доверенными. 

Если сервис размещён за reverse proxy, ограничьте сетевой доступ к API и отдельно спроектируйте доверенную конфигурацию прокси до начала использования forwarded-заголовков.

## База данных и эксплуатация

`internal/db/init.sql` описывает таблицы:

- `users`: профиль, хеш пароля, роль, статус и временные метки;
- `refresh_tokens`: хеш refresh-токена, пользователь, срок действия и признак отзыва;
- `api_rate_limits`: общие счётчики rate limiting.

Для refresh-токенов используется ротация: старый токен условно отзывается, состояние пользователя проверяется, новый хеш записывается в транзакции; новые cookie выдаются только после успешной фиксации. 

Повторное использование отозванного refresh-токена отклоняется и журналируется как событие безопасности.

## Известные особенности реализации

Эти пункты отражают текущее поведение кода, а не желаемую политику; сверяйте их с `docs/openapi.yaml` при изменениях:

1. **Login rate limit:** увеличивается на каждом запросе, включая успешный вход и запросы с некорректными credentials. Требование считать только неуспешные попытки требует отдельной доработки.
2. **Refresh rate limit без cookie:** запросы группируются по IP, а не по сессии, поскольку cookie отсутствует.
3. **Logout без refresh-cookie:** endpoint всё равно отвечает `200` и очищает cookie; если cookie передана, сервер пытается отозвать соответствующий токен. Ошибка отзыва приводит к `500`, cookie при этом очищаются.
4. **Статус пользователя:** middleware защищённых маршрутов проверяет активность и загружает актуальную роль из БД на каждом запросе; ошибка чтения пользователя не даёт доступ.
5. **Роль существующего пользователя:** PUT/PATCH административного пользователя не меняют роль; переданное поле `role` не является способом повышения/понижения роли. При этом `PUT /api/v1/users/{id}` требует поле `status` вместе с email, паролем и именами.
6. **CORS/CSRF:** CORS allow-list и CSRF Origin allow-list используют `CORS_ORIGINS`; все изменяющие методы требуют CSRF даже на публичных auth-маршрутах.
7. **Секрет регистрации администратора:** фактический обработчик читает `X-Admin-Token`; JSON-поле `admin_token` не используется, даже если оно встречается в более ранних примерах/спецификациях.
8. **Тестирование:** перед production-релизом запустите `go test ./...` и интеграционные проверки с PostgreSQL, включая конкурирующие refresh-запросы, недоступность БД, CSRF и rate limit на нескольких экземплярах.

## Безопасность

- Не используйте шаблонные секреты в production; `JWT_SECRET` должен быть случайным и не короче 32 символов.
- В production используйте HTTPS и `COOKIE_SECURE=true`.
- Не публикуйте `ADMIN_REGISTER_TOKEN` и не храните `.env` с реальными секретами в репозитории.
- Не открывайте PostgreSQL в интернет без необходимости; ограничьте сетевой доступ.
- Уточняйте и обновляйте документацию OpenAPI при любом изменении маршрутов, middleware, ответов и правил доступа.

## Тестирование и проверки качества

Unit-тесты не требуют запущенного PostgreSQL для тестирования HTTP middleware, в том числе ограничения частоты запросов:

```bash
go test ./...
go test -race ./...
go vet ./...
```

`TestRateLimit` использует потокобезопасное in-memory хранилище, поэтому проверяет HTTP-поведение лимитера без внешней базы. Проверяются прохождение запросов до лимита, блокировка сверх лимита, заголовок `Retry-After`, изоляция ключей, сброс окна, ошибки хранилища (fail-closed), некорректная конфигурация и конкурентные запросы. Это unit-тест middleware и не заменяет интеграционный тест SQL-запроса к PostgreSQL.

Для локальной интеграционной проверки rate limiting запустите PostgreSQL с `internal/db/init.sql` и проверьте отдельно, что таблица `api_rate_limits` существует, счетчики атомарно увеличиваются и разделяются между несколькими экземплярами приложения.

### Замечания по безопасности и поддержке

- Запросы к PostgreSQL используют параметризованные аргументы; не подставляйте пользовательский ввод в SQL-строки.
- Rate limiting отделен от HTTP middleware через интерфейс `RateLimitStore`; это позволяет тестировать политику независимо от инфраструктуры и при необходимости заменять backend.
- Глобальный лимит входа должен использовать нормализованный email как часть ключа, а не общий пустой ключ для всех аккаунтов.
- `go test -race ./...` полезен для обнаружения гонок в конкурентном коде; все новые изменения следует проверять им перед выпуском.
